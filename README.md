# Multi-Agent Traffic Light RL (SUMO)

Python-проект для multi-agent reinforcement learning управления светофорами в SUMO через TraCI.
Каждый traffic light system (TLS) считается отдельным агентом, но все агенты используют одну общую Q-сеть и один общий replay buffer.

## Что реализовано

- Independent DQN с parameter sharing на PyTorch.
- Один shared `QNetwork` и один shared `target network`.
- Общий replay buffer для transition'ов всех TLS.
- Связность TLS по графу из `net.xml`: соседи определяются по 1-hop дорогам между TLS.
- Observation включает локальные признаки TLS и mean-агрегаты соседей.
- Reward:

```text
r_i = -(waiting_i + alpha * queue_i) - beta * mean(waiting_neighbors + alpha * queue_neighbors)
```

- Ограничение `min_green`, чтобы агент не переключал фазу каждую секунду.
- Action space:
  - `0` - держать текущую фазу
  - `1` - переключить на следующую фазу TLS-программы, если это безопасно и прошло `min_green`
- Fixed-time baseline для сравнения: основной режим `fixed` использует исходные TLS-программы из `net.xml` без ручного `setPhase`.
- Метрики автомобилей и пешеходов сохраняются в `logs/`.

## Установка SUMO

Установите SUMO с официального сайта:

```text
https://www.eclipse.org/sumo/
```

После установки задайте переменную окружения `SUMO_HOME`.

Windows PowerShell, пример:

```powershell
[Environment]::SetEnvironmentVariable('SUMO_HOME', 'C:\Program Files (x86)\Eclipse\Sumo', 'User')
```

Также полезно добавить в `PATH`:

```text
%SUMO_HOME%\bin
```

TraCI не нужно ставить через pip: Python-модули `traci` и `sumolib` лежат в:

```text
%SUMO_HOME%\tools
```

Проект автоматически добавляет эту папку в `sys.path`, но `SUMO_HOME` должен быть задан до запуска Python/PyCharm. После изменения переменных окружения перезапустите терминал или PyCharm.

## Python-зависимости

Python 3.8+.

```bash
python -m pip install -r requirements.txt
```

В `requirements.txt` нет `traci`, потому что он поставляется вместе с SUMO.

## Запуск

Из корня проекта:

```bash
python main.py
```

В PyCharm можно запускать `main.py` через Shift+F10.

При первом запуске:

1. Проверяется SUMO, `SUMO_HOME` и импорт `traci`.
2. В `scenario/` ищется внешний SUMO-сценарий: сначала `*.sumocfg`, затем `*.net.xml` плюс `*.rou.xml`/`*.trips.xml`.
3. Если сценарий отсутствует, создается demo-сценарий с одним перекрестком и четырьмя направлениями.
4. Если нет `checkpoints/dqn.pt`, запускается короткое обучение.
5. Выполняется evaluation для RL и fixed-time baseline.
6. Метрики печатаются в консоль и сохраняются в `logs/`.

При повторном запуске checkpoint загружается, обучение пропускается, evaluation выполняется заново.
Checkpoint используется только если физически существует `checkpoints/dqn.pt`, файл не пустой и metadata
`checkpoints/dqn_meta.json` совпадает с текущим сценарием, TLS, числом фаз и размером observation/action.
Если checkpoint удален, поврежден или карта заменена на несовместимую, программа запускает обучение заново.

## Как подложить внешний SUMO-сценарий

Положите в папку `scenario/`:

```text
scenario/
  any_name.net.xml
  any_name.rou.xml
  optional.trips.xml
  optional.add.xml
  optional.poly.xml
```

Можно также положить готовый `*.sumocfg`. Если он найден, программа использует его как основной конфигурационный файл.

Запуск:

```bash
python main.py
```

Если `*.sumocfg` нет, программа сама создаст `scenario/autogenerated.sumocfg` с `net-file`, `route-files`, `additional-files`, `begin`, `end`, `step-length`, `no-step-log` и `quit-on-end`.

Fixed baseline - это исходные тайминги светофоров из `net.xml`. В режиме `fixed` код не вызывает `traci.trafficlight.setPhase`, SUMO сам выполняет программы светофоров.

RL evaluation - это управление теми же светофорами обученной DQN-моделью из `checkpoints/dqn.pt` с `epsilon=0.0`.

Если в маршрутах есть `pedestrians`, `person`, `personFlow` или `walk`, они будут симулироваться SUMO и логироваться в pedestrian metrics. Пешеходы пока не являются RL-агентами и не входят в reward.

Для разработки используются короткие значения в `src/training_params.py`:

```text
EPISODE_SECONDS = 300
TRAIN_SECONDS = 300
EVAL_EPISODES = 1
```

Для полноценного эксперимента их можно вручную увеличить до 3600.

Ключевые параметры обучения вынесены в `src/training_params.py`: `FORCE_RETRAIN`, `AUTO_RETRAIN_ON_SCENARIO_CHANGE`,
`EPISODE_SECONDS`, `TRAIN_EPISODES`, `EVAL_SEEDS`, параметры DQN, exploration и reward.

Пример текущего сценария:

```text
scenario/two_tls_corridor.net.xml
scenario/routes.rou.xml
scenario/trips.trips.xml
```

Если в сценарии несколько светофоров, агенты будут созданы автоматически по `traci.trafficlight.getIDList()`.
Граф соседей строится из `net.xml`: два TLS считаются соседями, если между ними есть дорога в топологии. Если надежно восстановить соседей нельзя, код использует пустые списки соседей и продолжает работать.

## Логи и checkpoint

- `checkpoints/dqn.pt` - веса DQN.
- `checkpoints/dqn_meta.json` - сигнатура сценария, TLS ids, размеры observation/action и параметры обучения.
- `checkpoints/config.json` - параметры запуска.
- `logs/train_metrics.csv`, `logs/train_metrics.jsonl` - лог обучения с epsilon, loss, replay size и действиями.
- `logs/eval_rl.csv`, `logs/eval_rl.json` - evaluation RL.
- `logs/eval_fixed.csv`, `logs/eval_fixed.json` - native fixed-time baseline.
- `logs/comparison.csv`, `logs/comparison.json` - сравнение.

В `logs/eval_rl.json` есть блок `action_stats`: сколько раз агент выбрал hold/switch, сколько switch заблокировал
`min_green`, и сколько раз реально был вызван `setPhase`. Если `phase_set_count = 0`, программа печатает warning.
В `eval_rl.json` и `eval_fixed.json` есть блок `pedestrian_metrics`.
## Сравнение с реальными таймингами светофоров

Чтобы сравнить RL с реальными или вручную заданными программами светофоров, положите файл:

```text
scenario/tls.add.xml
```

Файл должен быть SUMO additional XML и содержать `tlLogic`, например:

```xml
<additional>
    <tlLogic id="B1" type="static" programID="manual_fixed" offset="0">
        <phase duration="30" state="..."/>
        <phase duration="3" state="..."/>
    </tlLogic>
</additional>
```

При запуске:

```bash
python main.py
```

программа создаёт отдельные конфиги:

```text
scenario/autogenerated_native.sumocfg
scenario/autogenerated_real_timing.sumocfg
scenario/autogenerated_rl.sumocfg
```

`autogenerated_native.sumocfg` использует только тайминги из `net.xml` и не подключает `tls.add.xml`.
`autogenerated_real_timing.sumocfg` подключает `tls.add.xml` и даёт SUMO самому выполнять эти программы без `setPhase`.
`autogenerated_rl.sumocfg` по умолчанию тоже подключает `tls.add.xml`, чтобы RL управлял той же фазовой программой, но действия модели всё равно применяются через TraCI.

Основные результаты:

```text
logs/eval_rl.json
logs/eval_real_timing.json
logs/eval_fixed_native.json
logs/comparison_rl_vs_real_timing.json
logs/comparison_rl_vs_real_timing.csv
logs/comparison_rl_vs_fixed_native.json
logs/comparison_rl_vs_fixed_native.csv
```

Если `scenario/tls.add.xml` отсутствует, программа не падает: сравнение `RL vs real_timing` пропускается, а старый baseline `RL vs native fixed-time` остаётся рабочим.

Настройки находятся в `src/training_params.py`: `REAL_TIMING_FILE`, `RUN_REAL_TIMING_BASELINE`, `RUN_NATIVE_FIXED_BASELINE`, `PRIMARY_BASELINE`, `RL_USE_REAL_TIMING_PROGRAM_AS_BASE`.

## Сравнение пешеходных метрик

Пешеходные метрики сравниваются отдельно для `RL vs real timing` и `RL vs native fixed-time`.
В JSON comparison-файлах есть блок `pedestrian_comparison`, а в CSV добавлены плоские колонки с префиксом `pedestrian_`.

Правила расчёта:

- `pedestrian_arrived` считается как метрика на максимум: `(rl - baseline) / baseline * 100`.
- `pedestrian_avg_waiting_time`, `pedestrian_total_waiting_time` и `pedestrian_waiting_count` считаются как метрики на минимум: `(baseline - rl) / baseline * 100`.
- `pedestrian_running` выводится только как delta, потому что число пешеходов в сети в конце эпизода не всегда напрямую означает лучше/хуже без анализа arrived и travel time.
- Если baseline равен нулю, процент улучшения записывается как `null`, а в консоли выводится `n/a`.

## Алгоритм обучения

В текущей версии используется Double Dueling DQN. Все TLS-агенты по-прежнему используют одну общую shared Q-network и общий replay buffer, но расчет target и архитектура Q-сети расширены.

Double DQN снижает переоценку Q-values: следующее действие выбирается online-сетью, а значение выбранного действия оценивается target-сетью. Это отличается от обычного DQN, где target-сеть одновременно выбирает и оценивает максимальное действие.

Dueling DQN разделяет оценку состояния `V(s)` и преимущество действия `A(s,a)`. Итоговые Q-values считаются как `Q(s,a) = V(s) + A(s,a) - mean(A(s,*))`. Такой вариант позволяет сети отдельно учить полезность состояния и относительную полезность действий.

Параметры алгоритма находятся в `src/training_params.py`: `ALGORITHM`, `USE_DOUBLE_DQN`, `USE_DUELING_DQN`, `DUELING_AGGREGATION`, `MODEL_HIDDEN_DIM`, `MODEL_NUM_HIDDEN_LAYERS`, `MODEL_ACTIVATION` и `CHECKPOINT_VERSION`. При смене алгоритма или версии checkpoint старые веса не используются молча: metadata проверяет совместимость и запускает переобучение.

## Reward с учетом пешеходов

Основной приоритет reward остается автомобильным: модель минимизирует очереди и ожидание транспортных средств, а также учитывает состояние соседних TLS. Пешеходы добавлены как дополнительный малый штраф, чтобы их ожидание отражалось в обучении, но не доминировало над автомобильными компонентами.

Пешеходный компонент управляется параметром `REWARD_USE_PEDESTRIANS`. Его веса (`REWARD_PEDESTRIAN_WAIT_WEIGHT`, `REWARD_PEDESTRIAN_RUNNING_WEIGHT`, `REWARD_PEDESTRIAN_BLOCKED_WEIGHT`) намеренно ниже автомобильных весов (`REWARD_VEHICLE_QUEUE_WEIGHT`, `REWARD_VEHICLE_WAIT_WEIGHT`). Дополнительно применяется `PEDESTRIAN_REWARD_NORMALIZATION`, чтобы pedestrian penalty не становился главным источником reward.

В логах сохраняется `reward_breakdown`: автомобильный компонент, пешеходный компонент и `pedestrian_reward_share`. Если пешеходный компонент становится слишком большим, validation может завершиться ошибкой при `STRICT_REWARD_VALIDATION=True`.
